# Модуль анализа бизнес-процессов

Статус: проектирование первого этапа.

## Цель

Научить SA-Copilot восстанавливать наблюдаемый пользовательский процесс по тестовым материалам (скриншоты, видеозапись, позднее — разрешённая тестовая веб-форма), сравнивать варианты прохождения и готовить проверяемый черновик инструкции.

Модуль не заменяет аналитика и не объявляет гипотезы подтверждёнными бизнес-правилами.

## Границы первого этапа

Входит:
- фиксация сценариев и исходных параметров;
- фиксация действий пользователя и наблюдаемых реакций интерфейса;
- сравнение нескольких сценариев;
- разделение фактов, гипотез и неизвестных сведений;
- список вопросов и дополнительных экспериментов;
- подготовка структуры черновика инструкции.

Пока не входит:
- подключение к корпоративным источникам;
- автоматическое исследование рабочих систем;
- выполнение операций, меняющих данные;
- утверждение или публикация документов без проверки человеком;
- вывод причинно-следственной зависимости только из корреляции изменений.

## Принципы достоверности

1. Наблюдение должно ссылаться на источник: файл/видео и временную отметку либо номер кадра/скриншота.
2. Факт интерфейса отделяется от интерпретации его назначения.
3. Гипотеза не становится бизнес-правилом без подтверждения.
4. Если одновременно изменено несколько параметров, нельзя приписывать изменение результата одному параметру.
5. Для каждого вывода фиксируется статус: `observed`, `hypothesis`, `confirmed_by_analyst`, `unknown`.
6. Неизвестные значения не заполняются догадками.
7. Итоговые инструкции и сценарии — только черновики для проверки человеком.

## Модель данных сценария (черновая)

```json
{
  "scenario_id": "SC-001",
  "process_name": "Расчёт условий перевозки",
  "source_materials": [
    {
      "source_id": "SRC-001",
      "type": "video",
      "file_name": "demo.mp4",
      "observations": [
        {
          "timestamp": "00:00:12",
          "description": "Пользователь открыл форму добавления точки маршрута"
        }
      ]
    }
  ],
  "input_parameters": [
    {
      "name": "region_from",
      "value": null,
      "status": "unknown",
      "source_id": "SRC-001"
    }
  ],
  "user_actions": [],
  "system_responses": [],
  "calculation_result": {
    "value": null,
    "status": "unknown"
  },
  "observations": [],
  "hypotheses": [],
  "open_questions": [],
  "analyst_confirmations": [],
  "verification_status": "not_verified"
}
```

Это начальная схема для обсуждения. Поля будут уточняться до реализации хранения.

## Алгоритм обработки

1. Зарегистрировать исходные материалы и сценарий.
2. Извлечь наблюдаемые экраны, элементы и действия.
3. Восстановить хронологию действий пользователя.
4. Зафиксировать видимые реакции системы и результат.
5. Сопоставить сценарии и выделить изменившиеся/неизменившиеся параметры.
6. Если изменилось несколько параметров, сформировать гипотезы без однозначной причинной атрибуции.
7. Предложить дополнительные эксперименты для проверки гипотез.
8. Сформировать черновик инструкции и перечень пробелов.
9. Передать результат аналитику для проверки и подтверждения.

## Первый учебный кейс

Процесс: расчёт условий перевозки.

Исходный материал: демонстрационная видеозапись с несколькими вариантами расчёта, где одновременно изменяются несколько исходных параметров.

Важно: по одной такой записи можно зафиксировать наблюдаемое поведение и различия между вариантами, но нельзя достоверно установить влияние каждого отдельного параметра. Для этого нужны дополнительные контролируемые эксперименты.

## Критерии готовности первого прототипа

- [ ] Можно создать и сохранить сценарий.
- [ ] Для наблюдений можно указать источник и временную отметку.
- [ ] Параметры сценариев можно сравнить.
- [ ] Система показывает, какие параметры изменились.
- [ ] При множественных изменениях система явно предупреждает о невозможности однозначной причинной атрибуции.
- [ ] Факты, гипотезы и неизвестные сведения визуально и логически разделены.
- [ ] Можно сформировать черновик инструкции и список открытых вопросов.
- [ ] Все результаты обозначены как требующие проверки аналитиком.

## План разработки

1. Утвердить модель данных и словарь статусов.
2. Добавить модуль хранения сценариев без изменения существующего генератора требований.
3. Покрыть операции хранения и сравнения тестами.
4. Добавить интерфейс создания и просмотра сценариев.
5. Реализовать загрузку и анализ изображений.
6. Добавить обработку видео через извлечение кадров и временных отметок.
7. Подключить генерацию черновика инструкции.
