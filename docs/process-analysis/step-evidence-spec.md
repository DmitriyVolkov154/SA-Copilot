# Спецификация: шаги процесса и ссылки на доказательства

Статус: проектирование следующего этапа прототипа.

## 1. Цель

Научить SA-Copilot сохранять не только набор входных параметров и итог расчёта, но и последовательность действий пользователя с наблюдаемой реакцией интерфейса. Это станет основой для черновика пользовательской инструкции.

На этом этапе используются только синтетические сценарии и тестовые формы. Корпоративные источники, рабочие базы, внутренние API и служебные документы не подключаются.

## 2. Текущее состояние

В ветке `feature/process-analysis` реализованы ручное создание сценариев, локальное JSON-хранилище, сравнение входных параметров и результатов, разделение подтверждённых и неподтверждённых значений, а также предложения контрольных экспериментов.

Модель уже содержит поля `user_actions` и `system_responses`, но интерфейс не ведёт их как упорядоченные пары. Наблюдения и ссылки на материалы пока можно записывать только свободным текстом. Поэтому надёжно восстановить последовательность «действие → реакция системы» и привязать её к конкретному месту записи пока нельзя.

## 3. Предлагаемая модель шага

Добавить в сценарий массив `steps`. Один элемент — один наблюдаемый шаг процесса.

```json
{
  "step_id": "STEP-001",
  "order": 1,
  "action": {
    "text": "Пользователь выбирает значение в списке",
    "status": "observed"
  },
  "system_response": {
    "text": "В форме отображается новое значение",
    "status": "observed"
  },
  "evidence": [
    {
      "source_id": "SRC-001",
      "source_type": "video",
      "timestamp_ms": 12500,
      "frame_number": 38
    }
  ],
  "open_questions": []
}
```

Это синтетический пример структуры, а не описание реальной системы.

### Поля

| Поле | Назначение |
|---|---|
| `step_id` | Уникальный идентификатор шага внутри сценария |
| `order` | Порядок выполнения, начиная с 1 |
| `action.text` | Что сделал пользователь |
| `action.status` | Степень подтверждения действия |
| `system_response.text` | Что наблюдалось после действия |
| `system_response.status` | Степень подтверждения реакции |
| `evidence` | Ссылки на скриншот, кадр видео или ручную заметку |
| `open_questions` | Что осталось выяснить по шагу |

Допустимые статусы действия и реакции: `observed`, `confirmed_by_analyst`, `hypothesis`, `unknown`.

### Источники доказательств

Для первой версии достаточно типов:

- `screenshot` — отдельное изображение;
- `video` — временная отметка в записи;
- `browser_capture` — снимок или событие тестового браузера;
- `manual_note` — ручная заметка аналитика.

Для видео хранить `timestamp_ms`; для изображения — идентификатор изображения. Файлы материалов, если они сохраняются приложением, размещать только в локальной папке данных, исключённой из Git. Не записывать изображения и видео в репозиторий.

## 4. Правила достоверности

1. Действие пользователя и реакция системы — разные факты; их статусы проверяются независимо.
2. Нельзя выводить реакцию системы только из того, что пользователь нажал кнопку.
3. Если реакция не видна или неразборчива, записывать `unknown` и создавать открытый вопрос.
4. Назначение элемента интерфейса не выводить только из его подписи; при недостатке данных помечать интерпретацию как гипотезу.
5. Черновик инструкции строить по шагам со статусом `observed` или `confirmed_by_analyst`.
6. Шаги со статусами `hypothesis` и `unknown` не превращать в обязательные инструкции. Выводить их отдельно в блок «Требует проверки».
7. Каждый вывод по возможности должен содержать ссылку на источник и временную отметку/кадр.
8. Не считать совпадение во времени доказательством причинности.

## 5. Связь со сравнением сценариев

Массив `steps` дополняет, но не заменяет `input_parameters` и `calculation_result`.

Если между сценариями одновременно изменилось несколько подтверждённых входных параметров, модуль должен показать все различия и результаты, оставить `causal_attribution = not_established`, не приписывать результат одному параметру и предложить отдельные контрольные эксперименты. Неучтённые параметры и состояние системы также могут влиять на результат.

Сравнение последовательностей шагов можно добавить позднее. В первой реализации достаточно сохранять шаги и использовать их при подготовке инструкции.

## 6. Требования к интерфейсу следующей версии

1. Пользователь может добавить несколько шагов процесса.
2. Для каждого шага отдельно вводятся действие и реакция системы.
3. Шаги можно менять местами и удалять; порядок сохраняется после перезагрузки.
4. Для шага можно добавить тип источника и временную отметку/номер кадра.
5. Реакцию можно оставить неизвестной; интерфейс не подставляет текст автоматически.
6. Сценарии по-прежнему можно сравнивать без заполнения шагов.
7. Существующие сценарии без поля `steps` продолжают открываться; отсутствие поля трактуется как пустой список.
8. Данные остаются локальными в `data/`; исходные материалы не коммитятся в Git.

## 7. Критерии приёмки

- [ ] Сценарий с нулём шагов сохраняется и сравнивается как раньше.
- [ ] Сценарий с несколькими шагами сохраняет порядок после перезапуска приложения.
- [ ] Действие и реакция хранятся в одной записи шага.
- [ ] Неверный статус, отрицательный порядок или некорректная временная отметка отклоняются с понятной ошибкой.
- [ ] Отсутствующая реакция не превращается в выдуманный ответ системы.
- [ ] Ссылка на источник сохраняет временную отметку или номер кадра.
- [ ] Гипотеза и неизвестное не попадают в подтверждённую часть будущей инструкции.
- [ ] Существующие тесты сравнения и локального хранения не регрессируют.

## 8. Ограничения и порядок реализации

Текущий `qwen3:8b` используется как текстовая модель. Сам по себе он не анализирует изображения и видео. Поэтому сначала нужна ручная фиксация шагов и доказательств; локальное OCR/vision-распознавание и извлечение кадров — отдельный последующий этап после выбора и проверки совместимой модели на компьютере пользователя.

Рекомендуемый порядок:

1. Добавить валидацию и обратную совместимость поля `steps`.
2. Добавить редактор шагов в веб-интерфейс.
3. Покрыть модель и хранение тестами на синтетических данных.
4. Научить генератор собирать черновик инструкции из подтверждённых шагов и отдельно выводить вопросы.
5. Только затем исследовать локальный анализ скриншотов и видео.

Автоматизация браузера и любые подключения к рабочим системам в эту задачу не входят.
